# 权限矩阵与隐私开关设计

目标：让“隐私”成为产品能力，而不是只靠数据库 RLS。RLS 负责技术隔离，产品负责可理解的可见范围与授权体验。

## 1. 概念与对象

### 角色（当前）
- admin：家庭管理员
- parent：家庭成员（默认）
- child：未成年人/受限成员

### 数据域（未来可能扩展）
- Finance：交易、预算、分类
- Growth / Health / Relationships：高敏域，默认更严格
- Settings：家庭成员、邀请、角色

### 可见范围（推荐引入）
对每个“记录”引入 visibility 概念：
- family：家庭可见（默认适用于财务汇总类数据）
- private：仅本人可见（适用于高敏记录/不想共享的消费）
- restricted：仅指定成员/指定角色可见（后续迭代，可选）

## 2. 权限矩阵（MVP 版）

### 2.1 家庭与成员
| 功能 | admin | parent | child |
|---|---|---|---|
| 查看家庭信息（名称、创建时间） | ✅ | ✅ | ✅（可选隐藏部分） |
| 查看成员列表（昵称/角色） | ✅ | ✅ | ✅（仅昵称/关系） |
| 修改家庭名称 | ✅ | ❌ | ❌ |
| 邀请成员（生成/撤销链接） | ✅（推荐） | ✅（当前实现） | ❌ |
| 变更成员角色 | ✅（后续） | ❌ | ❌ |

### 2.2 财务交易（建议拆两层：记录与汇总）
| 功能 | admin | parent | child |
|---|---|---|---|
| 创建交易（family 可见） | ✅ | ✅ | ✅（可开关） |
| 创建交易（private 私密） | ✅ | ✅ | ✅（默认开启/关闭由家庭决定） |
| 查看 family 可见交易 | ✅ | ✅ | ✅（可开关：child 默认关闭或仅汇总） |
| 查看 private 私密交易 | ✅（仅本人） | ✅（仅本人） | ✅（仅本人） |
| 编辑/删除他人 family 交易 | ✅（可选） | ❌ | ❌ |
| 编辑/删除本人交易 | ✅ | ✅ | ✅ |

### 2.3 预算/分类
| 功能 | admin | parent | child |
|---|---|---|---|
| 查看预算与分类 | ✅ | ✅ | ✅（仅只读） |
| 修改预算与分类 | ✅ | ✅（当前可放开） | ❌ |

## 3. 隐私开关（产品层）

### 3.1 家庭级开关（管理员可配置）
- 是否允许 child 查看交易明细（默认否，仅看汇总）
- 是否允许成员创建 private 交易（默认是）
- 是否允许成员看到“谁创建了交易”（默认否，减少关系压力）

### 3.2 个人级开关（每个用户）
- 默认新交易可见性：family / private
- 是否在家庭里显示真实姓名（默认昵称）
- 导出范围：仅本人 / 家庭（取决于角色与政策）

## 4. 与数据库/后端的映射建议（为后续扩展做准备）

### 4.1 交易表扩展（建议）
- `visibility`：family | private | restricted
- `owner_user_id`：记录归属（private 必需）
- `shared_with`（可选，后续）：指定成员列表（restricted）

### 4.2 RLS 策略原则
- family 可见：必须是同一家庭成员
- private 可见：必须是 owner_user_id == auth.uid()
- restricted：必须在 shared_with 中

## 5. 交互与文案原则（降低隐私焦虑）
- 默认不强迫填写“备注/描述”
- 对高敏数据提示“可设为私密”
- 任何跨成员可见的内容，都要有明确标签（家庭可见/仅自己）

## 6. 审计事件（商业化前建议补齐）
- 邀请创建/撤销/接受
- 数据导出
- 账号注销/数据删除
- 角色与权限策略变更
