# 数据分级与数据流（Data Map）

本文用于把“我们到底收集/存储/处理了什么数据”说清楚，以支撑后续隐私政策、权限设计、删除/导出、保留期与商业化合规扩展。

## 1. 数据分级（建议）

### P0（高敏 / 高风险）
- 财务：交易金额、交易时间、分类、描述（描述可能包含更多个人隐私）
- 健康：体检、用药、病史、心理相关信息（若后续引入）
- 关系：家庭矛盾、沟通记录、事件日志（若后续引入）
- 未成年人相关：child 角色产生的任何可识别信息

### P1（敏感 / 可识别）
- 账号信息：邮箱、用户 ID（UUID）、姓名/昵称
- 家庭信息：家庭名称、家庭成员列表、角色
- 邀请：邀请 token、邀请绑定邮箱（如启用）

### P2（低敏 / 运营）
- 偏好与配置：主题、语言、显示偏好
- 统计与诊断：仅聚合后的使用行为（如后续接入分析/埋点）

## 2. 数据处理清单（按功能）

### 2.1 认证与账号（Supabase Auth）
- 数据：邮箱、密码（由 Supabase 托管/加密）、会话 token
- 目的：登录鉴权、会话管理
- 存储位置：Supabase Auth
- 风险点：账号接管、会话泄露
- 关键控制：强密码策略、会话失效、最小权限、禁止在日志中输出 token

### 2.2 用户资料（public.users）
- 字段：id、email、name、role、family_id、created_at、updated_at
- 目的：家庭成员协作、权限控制
- 可见范围：本人可见；家庭成员可见必要字段（最小化）
- 风险点：成员身份暴露、角色越权
- 关键控制：RLS + 产品侧权限矩阵 + 最小字段返回

### 2.3 家庭信息（public.families）
- 字段：id、name、created_at、updated_at
- 目的：组织边界与协作容器
- 可见范围：家庭成员
- 风险点：家庭名称可包含敏感信息
- 建议：提示用户避免写真实地址/电话号码作为家庭名

### 2.4 交易（public.transactions）
- 字段：amount、category、description、date、type、family_id
- 目的：记账、统计、预算与洞察
- 可见范围：默认家庭共享；可扩展“私密交易/个人账本”
- 风险点：description 极易包含敏感细节（医疗、关系、地点）
- 建议：
  - description 做“可选”并弱化输入引导
  - 后续引入“私密字段/私密交易”的产品开关与字段级加密策略

### 2.5 邀请（public.invitations + RPC）
- 数据：token、role、status、expires_at、family_id、email(可选)
- 目的：邀请加入家庭
- 可见范围：家庭成员（管理端）/ 通过 token 做最小化预检
- 风险点：token 泄露导致未授权加入
- 控制：过期时间、状态机、可撤销、可选 email 绑定、接受邀请时校验 email

## 3. 数据流（端到端）

### 3.1 创建家庭
1) 已登录用户调用 create_family RPC
2) 生成 families 记录并将 users.family_id 写入
3) 前端刷新 profile 与家庭数据

### 3.2 通过邀请加入
1) 用户打开 join 链接（token）
2) 前端调用 get_invitation_info 做最小化展示（家庭名/角色/过期）
3) 登录后调用 accept_invitation 完成加入

### 3.3 记账
1) 前端收集最小字段（金额/类别/时间/类型，描述可选）
2) 写入 transactions
3) 前端拉取并本地计算统计（或后续改为视图/物化视图）

## 4. 数据保留期（建议默认值，可后续配置化）
- 账号与家庭：用户存续期间保留；注销后进入删除流程
- 邀请：过期/撤销后保留 30~180 天用于审计与反滥用（商业化后更重要）
- 交易：默认长期保留（用户价值最大）；应提供导出与删除能力
- 日志：不记录交易明细；仅记录必要的安全事件与错误码，保留 7~30 天（视合规与排错需求）

## 5. 第三方共享与出境（待定项）
- 当前：主要第三方为 Supabase（存储与认证）
- 若接入：分析/埋点、OCR、银行导入解析等，都需要新增“第三方处理清单”和明确告知/同意

## 7. AI 模型配置数据（v2：个人级 + 平台共享池）
AI 模型清单子系统（「设置 → 我的 AI 模型」）涉及两张表，不触及家庭成员数据：
- `ai_providers`：模型清单，按 `owner_user_id` 分两域——NULL 为平台共享模型（人人可选用）；非空为用户私有模型（仅归属者可见可改，可绑定自己的 API Key）。**API Key 一律以 AES-256-GCM 密文存储（`api_key_encrypted`），仅服务端持 `AI_PROVIDER_ENC_KEY` 可解密；对外接口只回传掩码 `api_key_mask`，明文密钥不出服务端，用户之间互不可见对方密钥。**
- `user_model_prefs`：用户个人默认模型选择（每用户每能力 text/vision 各一条：user_id、capability、provider_id），属低敏感个人配置数据，仅本人可读；随账号删除级联清理。
- 两表 RLS 均为 service-role-only（无面向普通用户的直接读写策略）；可见域与写权限在服务端端点守卫校验：私有行仅归属者可管理；共享行写权限由环境变量 `AI_SHARED_POOL_EMAILS`（部署者邮箱白名单）控制，不设平台管理员角色/表。
- 保留期：共享池条目随平台运营存续；私有行与偏好随用户账号删除级联清理；变更通过 `updated_at` 留痕，用于审计与故障回溯。
